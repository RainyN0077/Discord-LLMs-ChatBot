# 代码审查修复计划

## 0. Git 分支策略

当前仓库基准分支 `main` 已作为历史存档保留。采取以下分支操作重建代码基线：

```
main (旧基线，存档) ──► 新建 base-v2 (新基准分支)
                              │
                              └──► feat/code-review-fixes (修复分支)
```

**操作步骤：**
1. 在当前 `main` 的 HEAD 上创建孤儿分支 `base-v2`，作为全新的仓库基准
2. 将本地 `main` 重命名为 `main-legacy` 存档
3. 将 `base-v2` 重命名为 `main`（替换旧基线）
4. 从新 `main` 创建 `feat/code-review-fixes` 分支进行全部修复工作
5. 所有 commit 信息使用中文

## 2. 详细实施步骤

### 步骤 1：Git 分支初始化（计划确认后执行）

```bash
# 1.1 保存当前 main 为存档
git branch main-legacy main

# 1.2 创建新基准分支（孤儿分支，干净历史）
git checkout --orphan base-v2

# 1.3 提交当前工作区作为新基准的初始提交
git add -A
git commit -m "初始化项目基准：Discord LLMs ChatBot 多功能 Discord 机器人"

# 1.4 替换 main 分支
git branch -D main
git branch -m base-v2 main

# 1.5 创建修复分支
git checkout -b feat/code-review-fixes
```

## 4. 风险评估

- **孤儿分支重建**：创建 `--orphan` 分支将丢弃所有 git 历史（10 个 commit），`main-legacy` 分支会保留完整历史作为备份。确认远程仓库 `origin/main` 不需要回退后，才可 force-push 新基准。
- **模块拆分（P1-5, P1-6）**：重构范围大，需确保导入路径正确。建议拆分后立即进行全功能冒烟测试。
- **版本锁定（P1-1）**：如果当前依赖有已知安全漏洞，锁定版本可能延迟修复。建议配合 `pip-audit` 使用。
- **知识管理器索引改造（P1-2）**：涉及 SQLite 表结构变更（添加列），需要在 `_ensure_runtime_schema` 中添加迁移逻辑，确保向后兼容。
- **配置缓存实现（P1-3）**：需要在 Commit 10/11（模块拆分）之前完成，确保拆分后的路由模块能直接使用缓存机制。拆分时缓存逻辑应随 `load_config`/`save_config` 函数迁入 `utils.py` 或新模块 `config_cache.py`。
